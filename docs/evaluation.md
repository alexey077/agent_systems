# Как проверяем качество и надёжность

Связанные требования: R04–R14. Записанный набор: `data/scenarios.json`, 21 синтетический случай. Это стартовый набор для ДЗ 1, не репрезентативная выборка граждан и не оценка готовности к промышленной эксплуатации.

## Три независимых слоя свидетельств

| Слой | Что выполняется реально | Что он доказывает |
|---|---|---|
| Unit/integration | Валидация, поиск, SQLite, таймауты, подтверждение, лимиты | Детерминированные свойства harness |
| HTTP-contract | MockTransport проверяет OAuth, request/response и перевод функций обоих API | Корректность кода адаптера на зафиксированном протоколе |
| Real-provider eval | Настоящие сетевые вызовы выбранной модели, 3–5 повторов | Наблюдаемое поведение данной модели на сценариях |

Offline `ScriptedProvider` содержит заранее заданные ответы и вызовы. Тест модели в этом режиме не проводится, качество LLM не измеряется. Все отчёты маркируются mode, provider и model. Скрипты не передаются реальному провайдеру при live-eval.

## Набор сценариев

| Группа | Проверки |
|---|---|
| Обычная работа | 5 предметных тем, оба порядка чтения инструментов |
| Приоритет | high только при наличии основания в тексте и справочнике |
| Временный сбой | Один timeout и успешный повтор |
| Постоянный сбой | Три timeout/недоступности, передача человеку |
| Результат сервиса | Пустой, некорректный, слишком большой, посторонние инструкции |
| Аргументы | Некорректный limit и исправление по ошибке |
| Неопределённость | Вне темы, неоднозначное сообщение, персональный статус |
| Человек и права | Отмена передачи и отсутствие права действия |
| Источники | Выдуманный source_id отклоняется и исправляется |
| Атака | Распознанная команда на раскрытие ключа не доходит до модели |

Дополнительные unit-тесты проверяют enum и типы, неизвестные поля/функции, дублирование задачи между перезапусками, изоляцию организаций, токены/стоимость, шаги/контекст/число вызовов, обрезанный ответ модели и сохранение результата при отказе хранилища.

## Запуск

```bash
pytest -q
appeals --config config/offline.toml evaluate --repeats 3 --output runtime/offline/report.json
appeals evaluate --repeats 3 --output runtime/gigachat/report.json
appeals --config config/ollama.toml evaluate --repeats 3 --output runtime/ollama/report.json
```

Для быстрого разбора одного случая: `appeals evaluate --scenario timeout_persistent --repeats 3 --output runtime/debug/report.json`.

Каждый повтор получает новый request_id, trace и модельный контекст. Кэш результата или история предыдущего повтора не используются. Детерминированные faults сбрасываются для каждого повтора. Подтверждения в eval-харнесе симулируются из разметки для синтетических данных; это тест подтверждения, не человеческое согласие в реальной эксплуатации.

Для реального провайдера CLI выводит в stderr событие `evaluation_progress` после каждого завершённого запуска: номер/общее число, scenario_id, повтор, pass/fail и проваленные проверки. Итоговый stdout остаётся JSON. Отчёт содержит `failed_scenarios` с количеством провалов по сценарию/критерию, а в каждом `runs[].diagnostics` — причины отклонения карточки, типы ошибок инструментов/провайдера и факт подтверждения. Это диагностика фактического результата, а не исключение неудачных запусков.

После исправления сохраняйте отчёт в новом каталоге, чтобы первый прогон и новые трассы остались доступны:

```bash
appeals evaluate --repeats 3 --output runtime/gigachat_after_fix/report.json
```

Первый реальный прогон: 42/63 успешных запуска; [разбор исходного отчёта, базы и всех трасс](gigachat_first_live_audit.json). Все 21 сценарий и пять исходных критериев сохранены. Регрессионные тесты в `tests/test_live_regressions.py` проверяют выявленные ошибки завершения и исправления, но их результат не подменяет новый real-provider eval.

[Повторный реальный прогон после исправлений](gigachat_after_fix_summary.json) для коммита `0ee219f`: 63/63 успешных запуска, category_accuracy=1, handoff_accuracy=1. Свидетельство — терминальная сводка и все 63 события прогресса пользователя; новый полный report и ручная проверка 27 текстов пока ожидаются. Первый результат сохранён для сравнения; значение 100% относится к пяти автоматическим критериям фиксированного синтетического набора.

## Что сохраняется и считается

Начиная с `evaluation_schema_version=2` дополнительно проверяется priority: high задан в разметке срочного сценария, по умолчанию normal. Добавлены `check_names` и `priority_accuracy`. Прежние 63/63 относятся к пяти прежним критериям; [содержательная проверка полного отчёта](draft_quality_review.md) выявила пять текстов для правки. Метрики прежних запусков не переписываются. Следующий прогон после правок текста сохраняйте в `runtime/gigachat_quality_fix/report.json`.

- В каждом прогоне: фактический `CaseResult`, использованные инструменты, длительность, trace_path, результаты проверок и pass/fail.
- В `diagnostics.successful_reads` сохраняются успешные чтения и найденные IDs, в `blocked_reads` — отклонённые повторные намерения с `attempts=0`. `tool_calls` считает запросы модели, включая заблокированные; это не число исполнений backend. После `repeat_limit` итог проходит все прежние проверки, а неверный результат остаётся провалом.
- category_accuracy: число допустимых категорий / все прогоны.
- handoff_accuracy: совпадение needs_human с разметкой / все прогоны.
- scenario_pass_rate: все ожидаемые проверки прошли / все прогоны. Проверяются также статус, наличие ожидаемых инструментов и источников.
- draft_ready_share: доля карточек draft_ready. Это техническая доля готовых черновиков в данном наборе, **не** доказанная доля качественно решённых реальных обращений без человека.
- median_seconds и total_tokens. Стоимость в карточке появляется только при заданных обеих ставках тарифа.

Ненулевой код выхода при любом провале нужен, чтобы CI/оператор не игнорировали ошибки. Падения отдельных критериев сохраняются, а не исключаются из знаменателя. Значения по scripted-набору не сравниваются с реальной моделью как accuracy LLM.

## Ручная оценка черновиков

Автоматическое совпадение темы не гарантирует качество ответа. Для реального прогона сотрудник дополнительно проверяет каждый черновик: соответствует ли вопросу, подтверждаются ли утверждения источниками, нет ли выдуманного личного статуса/срока/обещания, понятен ли следующий шаг, правильно ли выбрана ручная обработка. Рекомендуется приложить таблицу ошибок с source_id и trace, отдельно посчитать ошибки фактов и маршрутизации. LLM-судья и расширенный эксперимент ручной/чат/агент относятся к финальному проекту, а не выдаются за уже проведённые.

## Как интерпретировать результат

21 фиксированный синтетический сценарий и 63 запуска позволяют обнаружить типовые сбои и вариативность, но не гарантируют максимальную оценку или обобщение на весь поток ФНС. Повторяется вся выборка, не только удачные случаи. В итоговую сдачу включаются реальные данные прогонов, включая неудачи, версии конфигурации и описанные ограничения.

# Фактическая проверка ДЗ 1

Дата: 15.11.2026. Статусы относятся к проверенной версии и не являются обещанием оценки преподавателя.

## Выполнено в среде разработки

- Реализованы три предметных инструмента, полный цикл, два настоящих сетевых адаптера и отдельный scripted backend.
- 21 синтетический сценарий, по три независимых повтора в offline harness.
- Проверены права, подтверждение, отмена, запись/дедупликация, schema validation, ошибки, таймауты, некорректные источники и лимиты.
- HTTP-contract тесты проверяют native OAuth/функции/состояние GigaChat и формат альтернативного API без реальных ключей.
- Чистое окружение Python 3.12, без наследования глобальных пакетов: установка по `requirements-dev.lock` и editable install прошли.
- **93 теста прошли**, lint и проверка форматирования прошли.
- **21 сценарий × 3 повтора = 63 offline прогона, все ожидаемые проверки прошли.** Это результат harness, не accuracy реальной LLM. [Машиночитаемые результаты](offline_results.json).
- Source distribution и wheel успешно собраны через `python -m build --no-isolation`.
- GitHub Actions успешно прошёл на Python 3.11, 3.12 и 3.13 для первой реализации. [Актуальные прогоны](https://github.com/alexey077/agent_systems/actions) показывают состояние последующих коммитов.

## Попытка реального подключения 15.11.2026

`appeals doctor --live` выполнил ограниченные попытки подключения и завершился контролируемой ошибкой недоступности провайдера. Диагностические запросы **без авторизационных данных** к OAuth endpoint, текущему и прежнему адресу списка моделей получили HTTP 503, `server=envoy`, с сообщением об ошибке соединения с upstream до получения его заголовков. Это не ответ о неверном ключе. Список моделей, access token и ответы LLM не получены, поэтому реальные оценки качества не вычислялись.

Обнаруженная при первом запуске зависимость SOCKS-прокси включена в lock-файл, ошибка отсутствующего транспорта обрабатывается как configuration error. Проверка TLS не отключалась. Осталось повторить запуск из сети, доступной серверам провайдера; дополнительные Client ID/Secret не устраняют сетевую недоступность.

## Исправление TLS и диагностики 15.11.2026

Связанные требования: R10–R12 и R14; контракты трёх предметных инструментов не менялись. Исправлена потеря причины транспортной ошибки: раньше TLS, DNS и сеть ошибочно отмечались как timeout, а конечное сообщение скрывало даже HTTP 503. Теперь ошибки различаются, а `doctor --live` сохраняет результаты пройденных этапов и завершается ненулевым кодом при сбое или недоступной модели.

В native GigaChat автоматически подключается публичный корень из официальной инструкции провайдера. Сохраняются системные корни, добавляется `certifi`; глобальные хранилища не изменяются, `CERT_REQUIRED` и проверка имени включены. [Происхождение и SHA-256 сертификата](tls.md).

Проверено: 93 теста, включая TLS-корни/отпечаток, запрет отключения проверки, вложенную ошибку сертификата без повторов, DNS/сеть/прокси/таймаут с ограниченными повторами, сохранение HTTP-статуса, диагностику этапов, недоступную модель и отсутствие секретов в выводе. Lint, форматирование, 63 offline прогона и wheel/sdist прошли. Наличие и пригодность CA внутри wheel дополнительно проверены по DER SHA-256.

Повторная установка по lock-файлу и editable install успешны. Реальная команда `appeals doctor --live` после исправления получила `live_stage=oauth`, `oauth_ok=false`, `models_ok=false`, `live_error.type=service_unavailable`, HTTP 503 после трёх попыток. Это подтверждённая ошибка доступности в среде разработки. На момент этого прогона подключение на Mac ещё не было подтверждено; последующий успешный результат пользователя приведён ниже. Ответы модели этим запросом не проверялись.

## Успешное подключение на Mac 15.11.2026

Источник свидетельства — полный вывод команд, предоставленный пользователем после обновления до `9653d30`, установки зависимостей и editable install в Python 3.12 на Mac. Сам агент разработки эту команду на Mac не выполнял.

`appeals doctor --live` завершил этапы подключения: `credentials_present=true`, `tls_verification=true`, `gigachat_ca_bundled=true`, `oauth_ok=true`, `models_ok=true`, `live_stage=complete`, `configured_model_available=true`. API принял ключ и вернул список моделей, включая настроенную `GigaChat-2-Pro`.

Это закрывает проверку OAuth, TLS-соединения и наличия выбранной модели в списке на Mac пользователя. Последующий результат обычного `appeals demo` приведён ниже. Сценарий со сбоем подтверждён последующим прогоном ниже; 3–5 повторов оценки, альтернативный backend и видео пока не подтверждены. В среде разработки отдельный сетевой блокер HTTP 503 сохраняется.

## Обычный сценарий с реальным GigaChat на Mac 15.11.2026

Свидетельство — предоставленный пользователем вывод `appeals demo`: события инструментов и итоговая карточка обращения `appeal_8f361190379e`. Это один реальный запуск `GigaChat-2-Pro`, а не scripted backend и не оценка качества на полном наборе.

Модель запросила `search_knowledge_base` с темой `account_access` и запросом о восстановлении доступа; инструмент вернул `fns_account_access`. Затем модель запросила `get_routing_rules` для той же темы и получила учебного адресата. Оба вызова завершились успешно с первой попытки. Итог: `status=draft_ready`, `category=account_access`, `priority=normal`, `needs_human=false`, один источник ФНС, три шага модели, два вызова инструментов, 2103 токена. Передача человеку и запись задачи в этом сценарии не требовались.

По предоставленному выводу подтверждены реальная генерация, последовательный function calling, использование результатов инструментов и формирование итоговой карточки с источником. Полный JSONL-файл остаётся на Mac пользователя; в репозиторий не добавлялись сырые трассы, абсолютный путь пользователя или секреты. Стоимость не вычислялась: `estimated_cost=null`.

Следующий прогон R05/R08/R13 — `appeals demo --fault` — выполнен пользователем; свидетельство приведено ниже. Полная оценка R14 (21 сценарий × 3 повтора), альтернативный провайдер и видео остаются открытыми.

## Сбой инструмента с реальным GigaChat на Mac 15.11.2026

Свидетельство — предоставленный пользователем вывод `appeals demo --fault` для синтетического обращения `appeal_ba1518574895` с реальной моделью `GigaChat-2-Pro`. Искусственный сбой относится только к поисковому инструменту; модель продолжала отвечать через API.

`search_knowledge_base` завершил три ограниченные попытки с `timeout` и вернул `ok=false`, тип `timeout` и подсказку о передаче человеку. После этого модель запросила `escalate_to_operator` с причиной `tool_failure`. Терминал показал точную карточку действия; пользователь ввёл `ПОДТВЕРЖДАЮ`. В событии вызова указан `confirmed_by=demo_operator`; результат инструмента содержит `status=escalated`, `deduplicated=false`, `ticket_id=review_dd36033213d4a866` и время подтверждения. Запись подтверждена успешным ответом инструмента.

Итоговая карточка: `needs_human=true`, `status=escalated`, тот же `ticket_id`, пустые `draft_answer` и `sources`, три шага, два вызова инструментов, 3342 токена. Агент завершился штатно и не выдал неподтверждённый справочный ответ после отказа поиска.

По двум предоставленным запускам подтверждены нормальная обработка, ограниченные повторы при сбое, возврат ошибки реальной модели, выбор всех трёх предметных инструментов суммарно, согласие человека и создание задачи оператору (R02/R05/R08/R13). Это два единичных прогона, не полная оценка R14 и не свидетельство отмены/дедупликации на реальной модели. Видео R15, выступление R16, 63 запуска live-eval и реальная смена провайдера остаются отдельными незакрытыми пунктами.
